# 工程库与多方案比较

v0.9 的“工程库/比较”用于固定完整现场、保留多个修订，再用同一负载重新比较 3—6 个方案。它是独立的本地 IndexedDB 工程库；旧“我的作品”、旧自动备份和里程碑继续保留，不会被静默替换。它不是云备份。

## 保存和恢复完整现场

1. 点击“工程库/比较”，选择新建工程，填写名称与本次修订备注，点击“固定保存当前完整现场”。
2. 继续修改电路或程序后，选择已有工程再次保存，即增加一个固定修订。此前修订不会被覆盖或自动淘汰。
3. 点击“修订/恢复”选择目标。恢复前会先把当前现场另存为一个工程；这一步失败就不会替换工作台。
4. 重要作品使用“导出全部修订”。重新导入同一份文件不会重复增加修订。相同标识但内容不同会拒绝，避免覆盖另一份作品。

每次保存包含候选设计、已应用设计、未编译源码、真实运行快照、待生效输入、模块父层。恢复后保持暂停；候选与运行版本仍可不同。恢复过程中若玩家打开了另一作品或改动现场，迟到的恢复不会覆盖它，已生成的恢复前备份仍保留。

在共享房间里可以查看、导出和隔离比较；保存、迁入、删除及替换本地现场需要先离开房间。本地库操作不借协作入口写回服务器。

## 升级旧作品库

“升级旧作品库”先检查每一个历史修订，显示可迁入与损坏数量。确认后，新工程、修订和迁入标记在同一个 IndexedDB 事务中提交；只有事务成功才报告迁入完成。重复迁入相同来源不重复增加记录。旧库原文不删除、不重写，迁移面板打开期间本窗口的旧自动备份暂缓，关闭后恢复。每次预览独立拥有这份保护；前一次读取迟到或失败不会关闭后一次预览的保护，也不会把旧错误写进新预览。

若旧库有损坏修订，默认整批拒绝。玩家可先导出旧原文，再明确选择“只恢复有效记录，并隔离完整旧原文”。此操作保留原文和错误信息，不把损坏数据标为已修复。

## 容量不足或记录损坏

当前策略预算为 64 个工程、512 个修订、单工程 32 个修订、单修订 8 MiB、全库 128 MiB、32 份比较报告及 64 份隔离数据。这些是应用上限，浏览器可能更早拒绝写入，不能视为保证可用容量。真实浏览器验收覆盖超过 4 MiB 的多修订库增长、重载恢复、并发提交及事务中止；未宣称实测写满 128 MiB。

容量不足、权限撤销或事务失败时，原记录与工作台不变。可导出当前现场或库文件，再明确删除不需要的固定记录。程序不会为保存新记录自动丢弃旧版本。

“检查记录完整性”验证修订指纹和完整现场。某个修订损坏时，健康工程仍可读取；可明确隔离损坏修订并导出原文。如果元数据损坏或丢失而其他记录仍在，不会创建一个空库来冒充原库；错误面板提供“导出新库原始恢复数据”。原始恢复数据是排查证据，不会直接作为可信工程自动执行。

关闭页面后数据通常保留在当前浏览器的当前站点下，但清理网站数据、隐私模式及离线文件来源策略均可能影响持久化。请用工程文件另存重要作品。

## 运行共同负载

在比较区勾选 3—6 个工程，填写共同负载，再运行。也可直接点击两个可修改起点：

- **3 种正确实现**：单个 AND、NAND 接 NOT、德摩根四门电路。共同输入变化和检查相同，实际展开游戏面积分别为 1、2、4。
- **3 种完整 MCU 方案**：固定 CPU 配一拍 RAM、固定 CPU 配两拍 RAM、自定义中断 CPU 配一拍 RAM。共同传感输入、协议读回、记录提交和 DMA 复制合同相同，运行 4096 μs。

比较始终从每份固定候选设计的冷启动副本重新运行，不使用保存时的成功报告或运行快照冒充本次验证。候选源码、工作台运行时间、待生效输入和草稿均不改变。后台计算可用时使用独立 Worker；离线文件等不支持场景由后台模块明确回退。取消、预算不足、无效工程或缺失响应均不会算作通过。

报告固定合同哈希、展开输入负载哈希、种子、引擎版本、成本规则 `verification-v8-cost/1` 与采样规则 `sampled-response-v9/1`。历史报告规则变化时标记需要重测，不改写旧报告。

## 如何理解结果

| 指标 | 含义及限制 |
| --- | --- |
| 功能检查 | 同一测试合同中的真实端口、状态检查；面积较大不影响功能通过 |
| 游戏面积 | 按当前成本规则展开模块后的权重，不是晶体管数量或硅片面积 |
| 已识别容量 | 当前规则已识别的状态与存储配置位数；未识别模型另列数量，不冒充完整容量 |
| 采样时延 | 按共同间隔配对请求和响应，显示 p50/p95/最大值；同采样时刻的 0 不表示物理零延迟 |
| 已响应/虚拟秒 | 实际完成的配对响应数除以共同虚拟时长，不是本机速度或最大吞吐能力 |
| 故障与限制 | 失败检查、首个反例、运行问题、未知采样、待响应数量及未完成状态 |

不合成一个总分。相对首个功能通过方案显示差异：功能通过即可比较面积与已识别容量；时延与吞吐还要求双方测量完整、有请求、全部配对、没有未知采样。没有请求或尚有未响应请求时不会给出“优化成功”。

完整 MCU 示例的验收记录中，32 μs 共同采样得到 2112/2176/2176 μs 响应差；三者同一 4096 μs 窗口均完成 1 次请求，即 244.140625 次/虚拟秒。这个有限负载不能证明最大吞吐。寄存器流水线测试还实际比较了 1/2/3 位存储及 0/1/2 μs 采样响应差。

## 开发接口与事务边界

`ProjectsV9.createStore()` 返回显式库实例。常用接口为 `save(session, options)`、`load(projectId, revisionId)`、`revisions(projectId)`、`export(projectId)`、`importPackage(raw)`、`migrateLegacy(raw)`、`audit()`、`exportRaw()`。保存既有工程可传 `expectedRevision`；两个连接同时基于同一旧修订保存，只允许一个成功，另一个返回 `E_STORE_CONFLICT`。

工程包使用 `silicon-lab.project-package/2`，固定修订使用 `silicon-lab.project-revision/2`。依赖版本由完整工作台合同锁定。导入拒绝未知字段、篡改指纹、关联错误、访问器和不兼容现场。报告允许真实测量产生的有限小数，用排序 JSON 的 SHA-256 校验；电路定义仍遵守其整数规范。

`ComparisonV9.example()` 与 `terminalExample()` 返回 `{records, workload}`；`compare(records, workload, {signal, runner, onProgress})` 返回独立报告。负载为 `silicon-lab.comparison-workload/1`，内部沿用 v5 测试合同和 v6 波形声明，没有任意脚本。总预算为 60 秒墙钟和 4000 万工作量；每次子测试仍受原 8 秒与 500 万工作量限制。跨方案共享剩余预算，不为每个方案重新计满总预算。

库实现使用 IndexedDB 对象存储 `meta/projects/revisions/reports/quarantine`。事务内读取现有状态，校验最新修订后只更新变化的行。当前仍会读取全库目录与内容来执行一致性和容量检查，因此不承诺无限增长或任意大库恒定响应时间。
