# 云端芯片库与协作房间

> 自托管适配：本文保留旧版共享库与房间的业务设计。本站身份现由本地账号系统提供，SQLite 迁移由服务启动自动管理；下文托管登录、Sites 与 D1 的部署描述仅作历史背景。当前账号、数据卷、迁移和恢复步骤以 [运维说明](OPERATIONS.md) 为准。

版本：v0.3.0。本文记录当前实现；部署结果与整体验收见本次发布记录。

云端支持保存不可变芯片修订、按权限搜索和下载、邀请成员，以及最多 8 人共同编辑和观察同一房间。房间程序由服务器运行，浏览器接收共同快照。离线 `game/index.html` 保留单机功能，在线功能需要通过网站入口登录。

## 玩家使用

### 发布与下载芯片

先在「我的芯片」封装并保存作品，再进入「在线实验室 → 云端芯片库 → 发布我的芯片」。选择用途说明、标签、可见范围及许可。纯数字结构芯片和携带固件的完整模块均由服务器重新校验；上传成功后才产生云端修订。

作品默认 `private`，仅拥有者与获得该作品邀请授权的人可读。`site` 表示有网站访问权限且已登录的玩家可读，不会改变网站本身的访问范围。站内共享必须选择 MIT、CC BY 4.0 或 CC0；`private` 许可只能用于私有作品。

下载时选择指定修订，内容加入本地个人芯片库，不替换当前画布，不自动升级已放置的芯片。修改内部结构或固件后，需要另存芯片新版本再发布。旧云端修订内容不可覆盖；作品的可见范围和展示说明适用于其全部修订。

### 一起运行与修改

1. 应用当前设计，在「在线实验室 → 我的协作房间」选择「用当前电路创建房间」。服务器从初始状态创建共同运行现场。
2. 房间拥有者生成邀请码，选择「编辑者」或「旁观者」。受邀者登录网站后，在在线实验室粘贴邀请码。
3. 持有控制权的人使用房间横条上的运行、暂停、推进 1 μs 和复位按钮。其他人接收同一份权威快照。
4. 要改设计，先暂停房间，再选择「编辑电路」。修改留在当前浏览器草稿中，提交时逐对象检查是否与他人的改动冲突。
5. 成功提交后，所有成员同步到新工程，电路冷启动。冲突不会覆盖他人的结果；保留草稿，刷新共享状态后核对并重试。

共享环境下拉框支持数字输入、温度传感器、串口终端、供电域和导线连接开关。界面数值含义：温度为 0—125 ℃，串口为 0—255 的单个字节，供电与连接为 1 开、0 关。事件排在下一虚拟微秒，暂停时仅入队；推进或运行后才生效。导线开关改变既有连接是否启用，新增、删除或改接导线属于设计修改。

「退出并保留共享副本」把服务器最新工程和运行现场留在本地；「恢复进入前的本地工程」恢复进入房间时暂存的本地工程及快照。进入前的现场保留在本次页面会话中，不应把刷新页面当作可撤销的退出操作。

### 房间快照

「保存房间快照」保存的是当前服务器快照的本设备副本，放在此浏览器的本地存储，不创建云端历史快照库。换设备、清理浏览器数据或存储失败时不能依赖这个槽位。

「恢复房间快照」需要当前运行控制权。确认后，服务器校验工程哈希、依赖、事件队列和各实例状态，再让整个房间回到保存时刻，所有成员都会看到时间回退。快照必须与当前电路版本匹配；版本不符或格式错误时原房间保持不变。

房间横条的「复位」默认执行冷复位：易失状态和 RAM 恢复各模型初始值（Core8 RAM 为 0），保留 ROM 程序。API 另支持指定实例的暖复位，暖复位保留该实例的 RAM。复位事件在下一微秒执行，不把全局虚拟时间改回 0；要回到早先时刻，使用匹配的快照恢复。

## 权限与邀请码

| 角色或范围 | 权限 |
| --- | --- |
| 芯片拥有者 | 发布新修订、选择可见范围、创建与撤销作品邀请 |
| 作品受邀者 | 查看和下载指定作品的修订；不能代拥有者发布 |
| 房间拥有者 | 查看、编辑、管理邀请；可以接管当前运行控制权 |
| 房间编辑者 | 查看、提交暂停状态下的设计改动；控制权空闲后可取得并运行 |
| 房间旁观者 | 查看共享工程与状态；不能编辑、运行、复位或恢复 |

网站访问权限与邀请码是两层独立权限。邀请码不会把私有网站变公开，也不会赋予网站访问资格；拥有者仍需通过网站分享设置允许受邀者访问。进入网站后，邀请码才授予对应芯片或房间的应用内权限。

邀请码为随机令牌，数据库只存其 SHA-256 摘要。有效期为 7 天，同一邀请码可以邀请多人；房间总人数包括拥有者，最多 8 人。加入人数检查与授权写入在同一 SQL 语句内完成，并发加入不能超过上限。

7 天限制的是接受邀请的期限，已授予的访问不会仅因令牌到期自动消失。拥有者撤销邀请时，同时删除仍由该邀请授予的访问。若成员后来通过另一份邀请取得新授权，旧邀请的撤销不删除新授权。服务端在读权限之外，还会在房间提交的原子写入条件中重新检查编辑权限，避免撤销与提交交错时出现越权写入。

身份取自 Sites 登录层注入的 `oai-authenticated-user-id`。生产服务不接受请求 JSON 中声明的用户，不包含测试身份或绕过认证的默认用户。自建部署需要提供同等可信认证入口，并移除客户端自行提交的同名身份头，不能直接公开一个信任任意请求头的 Worker。

## 权威运行与并发

当前采用有序 HTTP 请求和轮询，没有使用 WebSocket 或 Durable Objects。浏览器控制者运行时约每 250 ms 请求服务器推进最多 5000 μs；暂停时约每 900 ms 发送心跳。其他成员按房间状态轮询。网络时间和虚拟时间不同，后台标签页、断网或浏览器节流会降低推进速度。

每次操作读取持久化工程和快照，在服务器恢复 `CircuitLab.Runtime`、执行操作，再用数据库行的 `revision` 比较并交换（CAS）写回。只有成功写回的结果成为权威状态；并发请求不能各自覆盖同一个旧版本。没有浏览器运行时充当最终裁决者，也没有依赖 Worker 进程内存保存房间的唯一状态。

运行控制权属于一个已授权用户，租约 5 秒。控制者离线、权限撤销或心跳过期后，下一次访问会释放控制权并暂停房间。服务器不会在没有请求时自主执行后台仿真。取得控制权、租约失效、设计提交、复位和快照恢复都会更新 `epoch`；旧代次的运行指令被拒绝。

编辑采用 `{kind,key,before,after}` 差异。不同对象的改动可以在重新读取并重试后合并；同一个对象的 `before` 与服务器当前值不同则返回冲突，撤销也是相同规则。一批改动先全部验证，再整批保存，不保留半套修改。已有芯片的同一 `stableId + revision` 不能被原地改写，新增依赖时由服务器同步生成锁定记录。

幂等记录按真实用户与客户端 ID 的二元组隔离。新客户端从 `sequence=1` 开始，成功操作递增；重复发送最近一次完全相同的序号和内容不会再次推进时间。同序号不同内容、已过期序号或缺号会被拒绝。客户端应稳定复用自己的 ID，并在断线后读取服务器回执再决定重试，不能用随机新 ID 绕开幂等检查。

## API

统一前缀 `/api`，请求与响应为 JSON。写入拒绝不同来源的 `Origin`；响应使用 `Cache-Control: no-store`。未知字段、危险对象键、重复 JSON 键、非法数值和不支持的信号编码都会失败。

| 方法与路径 | 作用与主要参数 |
| --- | --- |
| `GET /session` | 当前真实用户、版本、限制、`transport: ordered-http` |
| `GET /library?q=&offset=` | 只搜索可访问作品；每页 30 条，返回 `next` |
| `POST /library` | `requestId, package`；可带 `title, description, tags, license, visibility, baseRevision` |
| `GET /library/:id?revision=N` | 获取可访问作品的指定修订；未指定时取最新 |
| `GET /rooms` | 当前用户可访问的最近 30 个房间 |
| `POST /rooms` | `workspace` 与可选 `title`，从工程初始状态创建 |
| `GET /rooms/:id` | 共享工程、快照、修订、代次、控制者、成员与最近操作 |
| `POST /rooms/:id/operations` | `{clientId,sequence,epoch,operation}` |
| `POST /invites` | `{kind:"chip"或"room",resource,role}`；仅拥有者 |
| `GET /invites` | 本人发出的最多 100 条邀请，不返回明文令牌 |
| `POST /invites/join` | `{token}`，接受对应授权 |
| `DELETE /invites/:id` | 拥有者撤销该邀请及其仍然有效的授权 |

发布用 `requestId` 实现幂等：相同用户、相同 ID、相同请求返回原回执；改变内容后必须使用新 ID。已有作品发布还必须携带当前 `baseRevision`。云端修订号与芯片内部修订号分别保存；同一个已发布内部版本不能换成不同结构或模块运行内容。

运行 `operation` 的字段如下。未列出的字段不接受。

| `kind` | 附加字段 | 行为 |
| --- | --- | --- |
| `acquire` | 无 | 取得控制权，暂停并更新代次 |
| `patch` | `changes` | 验证并提交设计差异，冷启动 |
| `heartbeat` / `run` / `pause` | 无 | 续租、设置共享运行或暂停 |
| `advance` | `microseconds`，可选布尔 `single` | 推进 1—5000 μs；暂停时必须明确 `single:true` |
| `input` | `port,value` | 排队数字输入，数值或合法 `X/Z`、四态向量 |
| `temperature` | `path,value` | 指定 I²C 温度设备，0—125 整数 |
| `terminal` | `path,byte` | 指定实际终端，发送 0—255 单个字节 |
| `power` | `domain,enabled` | 指定供电域，`enabled` 必须为布尔值 |
| `connection` | `path,enabled` | 指定现有连接，严格布尔开关 |
| `reset` | 可选 `mode,target` | `warm/cold`，默认 `cold`；默认目标 `all` |
| `restore` | `snapshot` | 校验后恢复整个共享现场，暂停并更新代次 |

`patch` 由逐对象冲突检查决定是否可合并，不要求提交者仍处于相同工程代次。运行操作必须由当前控制者以正确代次提交。响应包含最新 `revision`、`epoch` 和快照，客户端不能根据按钮动画推定操作已成功。

错误响应为 `{error,code}`。常见状态：400 格式或运行契约错误；401 未认证；403 权限或跨来源写入被拒；404 不存在或不可访问；409 版本、序号、控制权或编辑冲突；413 超过请求或工程预算；429 房间客户端记录已满；503 数据库绑定未就绪。失败不会消费成功操作序号。

| --- | --- |

| 房间成员 | 8，含拥有者 |
| 房间客户端幂等记录 | 64 个逻辑客户端；不是额外的成员名额 |
| 待处理外部事件 | 256 |
| 单次编辑差异 | 1—3000 个，不允许重复编辑同一对象 |
| 单次仿真推进 | 1—5000 μs |
| 房间操作日志 | 最近 100 条 |
| 名称 / 用途说明 / 标签 | 80 / 1000 字符；最多 6 个不重复标签，每个最多 24 字符 |

展开预算也检查保留的结构定义，避免用短文件引用大量嵌套实例绕过运行规模限制。所有限制超出时明确拒绝，不截断电路、静默丢掉标签或伪称仿真已完成。

客户端记录是有界历史，稳定复用 ID 可避免频繁进出消耗额外记录。v0.3 没有自动清理发布历史、云端房间回收站或云端历史快照浏览器；这些不能由现有本设备快照按钮替代。

## 部署与迁移

正式入口为 `app/api/[...path]/route.ts`，把 Sites/Worker 的 `env.DB` 交给 `server/cloud.mjs`。数据库使用 Cloudflare D1；schema 在 `db/schema.ts`，已生成的首次迁移为 `drizzle/0000_whole_doctor_octopus.sql`。`.openai/hosting.json` 的 D1 绑定名为 `DB`。v0.3 本次云端审查未改变 schema，不需要为权限和并发修复新增迁移。

维护顺序：

1. 使用项目的依赖安装与构建流程；canonical 游戏源是 `game/`。先执行 `node scripts/sync-game.mjs` 同步到 `public/game/`，再执行 `npm run build`。
2. 核对目标环境真实的 D1 `DB` 绑定。构建产物中的本地占位数据库 ID 不代表生产绑定，也不能作为生产创建或覆盖数据库的依据。
3. 首次部署前，将 `drizzle/` 中尚未执行的迁移应用到对应数据库。生产通过托管发布流程管理迁移记录；已经执行的首次 `CREATE TABLE` 脚本不能每次启动重复执行。
4. 本地 Worker 使用 `dist/server/wrangler.json`，项目 `npm run start` 以本地持久化模式运行。验证应使用隔离数据库，再检查实际 Worker/D1 绑定；不能把测试预览的内存数据库当作部署成功证据。
5. 发布前检查未登录请求返回 401、私有作品跨身份不可读、并发提交冲突无部分写入，以及迁移后已有工程能恢复。生产身份依赖可信网站登录层，不把 QA 身份注入搬入生产代码。

后续修改 schema 时，通过 `npm run db:generate` 生成新迁移，审查增量后再执行；不要修改已应用迁移来伪装升级。更换引擎时还需考虑快照 `engineVersion`、工程哈希及模型兼容性，不能在校验失败时丢弃状态并假装正常恢复。

## 已完成的验证与限制

`node --test tests/cloud-v3.test.cjs` 的 33 组真实 SQLite 业务测试通过（最初 31 组，加上 Build8 来源互通与初始视图步长两组回归）。适配器使用 Node 的 `node:sqlite` 执行实际表、唯一索引、SQL 条件和事务，不以 JavaScript 对象冒充持久化数据库。

覆盖登录与来源检查、私有搜索和下载隔离、发布幂等与不可变版本、并发发布、邀请超员与撤销竞态、提交时权限复核、CAS 冲突及独立改动重试、冲突撤销、非法 patch、依赖锁、严格外部事件、冷暖复位、快照恢复、流式请求预算与展开预算。

Build8 编辑器使用 `sources["build8:" + 元件ID]` 保存源码草稿；服务器允许这个前缀，后缀仍必须是安全元件 ID，不接受路径穿越或额外冒号。实际执行依据 ROM 参数中的内容和源码，随工程及芯片内容哈希一起校验。回归通过真实 `BuilderMCU.build`、`applyProgram` 修改程序，创建共享房间并推进，又发布、下载并重新运行，确认输出为 13。流水灯初始视图中的 `suggestedStepUs:1` 也可原样创建房间；该可选字段只接受 1—100000 的整数，不改变仿真器信号或时钟规则。

8 成员固定负载测试执行 120 次推进，每次 10 μs；周期性让所有成员读取并比对相同快照，重发已提交事件验证不重复执行，最终时间为 1200 μs、房间修订为 120、日志保持最近 100 条。持久化测试关闭 SQLite 文件连接后重新打开，继续检查权限、实际 MCU RAM、共同快照以及发布与操作的幂等回执。

这些结果证明所测业务序列及故障边界，不代表容量或延迟保证。**尚未完成 30 分钟墙钟多人压力测试**，也未由这组测试证明跨地区网络、大量房间同时运行或生产 D1 限流情况下的长期性能。浏览器联调、真实 Worker/D1 烟测与实际部署结果由独立发布验收记录说明。
